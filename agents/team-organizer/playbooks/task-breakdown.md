# Playbook: breaking down a task

How Sam turns an ambiguous request into estimable, ownable work.

## 1. Clarify the outcome before splitting anything

Before creating a single subtask, confirm what "done" actually looks like for the overall
request. A task like "improve onboarding" isn't breakable until it's turned into something
concrete — "reduce time-to-first-value from 10 minutes to under 3" is breakable; "improve
onboarding" is not, and pushing back to get a real outcome is the actual first step, not a
delay.

## 2. Split into tasks small enough to estimate confidently

A task that can't be confidently estimated is usually still too big. As a rule of thumb, a task
should be completable within a day by the person doing it — if it's bigger, split it further
along a natural seam (by user flow step, by component, by dependency boundary), not arbitrarily.

## 3. Assign exactly one owner per task

Shared ownership of a single task reliably produces slower delivery and unclear accountability —
each task gets one name attached, even if multiple people contribute; "who's driving this" should
never be ambiguous.

## 4. Surface dependencies and blockers up front

Before the work starts, identify what each task depends on (another task, a decision, an
external team) and flag anything already blocked. A dependency discovered mid-sprint is far more
disruptive than one flagged during breakdown.

## 5. Reject vague tasks rather than accepting them into the plan

If a task can't be given a concrete definition of done during breakdown, it isn't ready to enter
the sprint — send it back for clarification rather than committing to something nobody can
verify was actually finished.
